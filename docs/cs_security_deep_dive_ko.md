# CS 및 암호학/네트워크 보안 심화 분석 (Deep Dive)

본 문서는 FIDO2 Proof-of-Possession (PoP) 아키텍처의 토대를 이루는 암호학, 네트워크 보안, 시스템 설계 원리를 패킷과 메모리 수준에서 분석합니다.

---

## 1. 비대칭키 암호화 및 디지털 서명 (ECDSA P-256 vs RSA)

### 타원곡선 암호(ECC)의 원리와 P-256 선택 배경

RSA 알고리즘이 소인수분해의 난해함에 보안 근거를 두는 반면, ECC(Elliptic Curve Cryptography)는 유한체 위의 타원곡선 이산 대수 문제(Elliptic Curve Discrete Logarithm Problem, ECDLP)를 기반으로 합니다.

본 시스템이 **NIST P-256 (secp256r1)**을 채택한 이유는 두 가지입니다.
1. **키 길이 효율성**: RSA에서 동일한 128비트 보안 강도를 얻으려면 3,072비트 키가 필요하지만, ECC는 256비트 키로 같은 수준을 달성합니다.
2. **전송 오버헤드 절감**: 서명 데이터 크기가 약 64 Bytes에 불과해, 매 HTTP 요청 헤더에 서명을 첨부해야 하는 PoP 아키텍처에서 네트워크 페이로드를 실질적으로 줄일 수 있습니다.

### 서명 생성(Sign)과 검증(Verify)의 수학적 흐름

1. **생성(Sign)**:
   - 임의의 난수 $k$를 선택하고 타원곡선 연산으로 점 $(x_1, y_1)$을 구합니다.
   - 메시지 다이제스트(SHA-256) $z$, 개인키 $d$, $x_1$을 이용해 서명값 $(r, s)$를 계산합니다. 이 두 값은 Base64로 인코딩되어 HTTP 헤더에 실립니다.

2. **검증(Verify)**:
   - 수신자는 서명 $(r, s)$, 원본 메시지 해시 $z$, 그리고 송신자의 공개키 $Q$를 전달받습니다.
   - 매개변수 $u_1, u_2$를 계산한 뒤, 기준점 $G$와 공개키 $Q$를 선형 결합하여 $R' = u_1 \cdot G + u_2 \cdot Q$를 도출합니다. 이는 이산 대수의 역산이 아닌 정방향 연산임에 유의합니다.
   - $R'$의 x좌표 $x_{R'}$이 $r$과 법 $n$에 대해 합동($x_{R'} \equiv r \pmod n$)이면 서명이 유효합니다.

## 2. HTTP 요청 정규화 (Canonicalization)와 무결성 보장

토큰 자체에만 서명하는 방식은 충분하지 않습니다. 탈취한 서명을 다른 엔드포인트 호출이나 변조된 페이로드에 재활용할 수 있기 때문입니다. 이를 막기 위해 HTTP 요청의 핵심 컨텍스트를 단일 바이트 문자열로 직렬화하는 **정규화(Canonicalization)** 파이프라인을 적용합니다.

### 파이프라인 구조
```text
SigningPayload = HTTP_METHOD | URI_PATH | SHA-256(BODY) | NONCE | TIMESTAMP
```

### 스트리밍 처리와 메모리 복잡도

`SigningPayload`에 Body 원문 대신 `SHA-256(BODY)` 다이제스트를 사용하는 것은 단순한 관례가 아니라 메모리 관리 측면의 의도적인 설계 결정입니다.

리버스 프록시는 대용량 페이로드를 업스트림으로 전달할 때 통상 청크 단위 스트리밍(Chunked I/O)을 사용합니다. 이때 Body 원문을 정규화 문자열에 직접 결합하려 하면, 서명 검증을 위해 전체 페이로드를 단일 메모리 버퍼에 다시 적재해야 하는 문제가 생깁니다. 반면 다이제스트만 사용하면 스트림을 그대로 통과시키면서 `hasher.update(chunk)` 호출로 해시를 점진적으로 누적할 수 있습니다.

결과적으로 검증 레이어에서 발생하는 부가적인 메모리 오버헤드는 SHA-256 다이제스트 크기인 32바이트로 고정되며, 해당 작업의 공간 복잡도(Space Complexity)는 $O(1)$로 유지됩니다.

### 페이로드 변조(Tampering) 방어

중간자(MitM) 공격으로 `GET /api/v1/data`가 `POST /api/v1/admin`으로 변조된 경우를 예로 들겠습니다.

게이트웨이는 수신한 실제 요청을 기반으로 `SigningPayload`를 재구성합니다. 경로가 달라졌으므로 해시 입력값이 바뀌고, 원래 서명과 일치하지 않아 `403 Forbidden`을 반환합니다. Method, Path, Body, Nonce, Timestamp 중 어느 하나라도 변조되면 같은 방식으로 탐지됩니다.

## 3. 재전송 공격(Replay Attack) 방어 및 이중 DoS 방어

서명된 요청 전체를 가로채 서버에 그대로 재전송하는 공격에 대해, 게이트웨이는 **일회용 난수(Nonce)**와 **타임스탬프(Timestamp)**를 조합하여 방어합니다. 그런데 난수 발급 엔드포인트(`/auth/nonce`) 자체가 서비스 거부(DoS)의 공격 면이 될 수 있습니다. 이를 위해 시스템은 성격이 다른 두 가지 방어 계층을 함께 운용합니다.

### 3.1. L7 Ingress Flooding Mitigation (단기 폭증 방어)

봇넷이 인증 없이 Nonce 발급 요청을 쏟아내어 CPU와 네트워크 자원을 소진시키는 볼류메트릭(Volumetric) 공격에 대응합니다.

`app/core/rate_limiter.py`는 클라이언트 IP를 키로 삼아 **슬라이딩 윈도우(Sliding Window)** 알고리즘으로 요청 빈도를 추적합니다. 단일 IP가 초당 10회(10 req/s)를 초과하면 즉시 `429 Too Many Requests`와 `Retry-After: 1` 헤더를 반환하고 처리를 중단합니다. 이후의 검증 로직은 전혀 실행되지 않습니다.

### 3.2. State Accumulation Prevention (장기 상태 누적 방어)

정상적인 속도로 Nonce를 발급받은 뒤 실제 요청에는 사용하지 않는 패턴이 반복되면, 백엔드 메모리에 미사용 상태가 서서히 쌓입니다. `app/core/nonce_store.py`는 이를 세 가지 방식으로 제어합니다.

1. **스레드 안전성(Thread-Safety)**: `threading.Lock()`으로 멀티스레드 환경의 동시 접근을 직렬화하여 경쟁 상태(Race Condition)를 제거합니다.
2. **슬라이딩 윈도우 TTL (60초)**: 발급된 모든 Nonce는 60초 후 자동으로 만료됩니다.
3. **가비지 컬렉션(GC)**: 만료된 항목을 주기적으로 순회하며 삭제합니다. 타임스탬프 자체가 60초를 초과한 요청은 캐시 조회 없이 즉시 거부합니다.

## 4. FIDO2 / WebAuthn 하드웨어 바인딩의 특성

DPoP 같은 소프트웨어 기반 인증키 모델과 구별되는 FIDO2의 핵심은, **개인키가 호스트 OS의 메모리에 절대 노출되지 않도록 하드웨어 수준에서 격리(Hardware Isolation)**한다는 점입니다.

### OS 및 보안 모듈과의 통신 흐름

1. 클라이언트(웹 브라우저)가 JavaScript `navigator.credentials.get()` API를 호출합니다.
2. 브라우저는 OS의 WebAuthn 구현체(Windows Hello, macOS TouchID 등)로 제어를 위임합니다.
3. OS는 서명 챌린지(Challenge)를 **TPM(Trusted Platform Module)**, 모바일의 **Secure Enclave**, 또는 외장형 **YubiKey(CTAP2 프로토콜)** 중 해당 하드웨어로 전달합니다.

### 추출 방지(Anti-Exfiltration) 설계

OS 커널 권한을 탈취한 루트킷이나 브라우저 제로데이가 발생하더라도 개인키 자체는 유출되지 않습니다.

보안 칩은 외부에서 챌린지를 받아 내부 논리회로에서 서명 연산을 수행한 뒤, **결과(Signature)만을 외부 버스로 내보내도록** 설계되어 있습니다. 개인키를 메모리로 읽어내는 명령어 자체가 존재하지 않기 때문입니다. 사이드 채널 공격이나 물리적 칩셋 리버스 엔지니어링을 제외하면, 이 구조는 키 유출에 대해 매우 강한 보장을 제공합니다.
